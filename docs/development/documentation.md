# 文档维护约定

## 按读者和时效选目录

| 目录 | 内容与边界 |
|---|---|
| `user/` | 用户完成某项操作所需的步骤、状态含义与问题反馈 |
| `operations/` | 管理员可复用的部署、配置、升级、诊断和恢复方法 |
| `architecture/` | 架构原理与协议说明，引用负责该契约的工程规范和 Schema |
| `development/` | 开发环境、验证方法和维护流程 |
| `roadmap/` | 当前未完成的路线与待办，不将计划写成已交付能力 |
| `decisions/` | 稳定编号的设计决策及其理由 |
| `archive/` | 带日期的交付、事故、升级和调研事实快照 |

`docs/README.md` 只做读者导航，各子目录 README 索引该目录的文档。
持续维护的文件采用主题名，不加任务编号或日期。ADR 编号与历史归档中的任务编号保留。
单次工程任务的 PRD、设计、实施和验证放在 `.trellis/tasks/<task>/`，不散落在 docs 根目录。

## 分离当前规则与历史事实

- 手册维护当前可复用的步骤；特定需求 ID、候选 SHA、某次测试结果与当时部署状态归档。
- 混合文档拆分时先保留完整原文快照，再提取手册，原来的失败、未验证项和更正必须保留。
- 历史正文不改写为当前结论；允许修正导航目标，需在迁移记录中注明并记录前后 SHA-256。
- 旧 Task 的 allowed_paths、context JSONL、已封存 evidence 属于当时事实，不做全仓字符串替换。
  旧路径的查找通过[迁移记录](../archive/README.md#document-migrations)完成。
- docs 解释原理和用法，`.trellis/spec/` 负责输入输出、不变量和测试要求，`schemas/` 负责机器协议。
  同一规则引用其负责模块，避免复制出多个互相冲突的版本。

## 移动文档的检查清单

1. 记录来源 Git revision、旧路径、原文件摘要和新位置；若包含未提交内容，明确记录来源是工作区快照。
2. 调整 Markdown 行内链接、引用式链接和章节锚点；路径从文档所在目录计算。
3. 更新根 README、AGENTS、当前工程规范与目录索引中的有效入口。
4. 归档只调整导航，不改变原文中的执行结果；迁移清单记录这些修订，不覆盖旧迁移记录。
5. 检查各目录索引覆盖、旧路径残留、链接/锚点、原文保留和 `git diff --check`。
   纯文档迁移使用这些检查，不将未执行的业务测试写成通过。
