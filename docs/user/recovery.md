# 交付中断与问题反馈

## 继续原需求

1. 打开原需求，查看当前阶段、最近操作结果和阻塞原因。
2. 若需要补充知识，先按[知识确认流程](knowledge.md)处理。
3. 需要继续执行时点击一次“继续交付”，等待平台返回结果。
4. 若出现候选复核或 Coder 恢复计划，核对候选、范围和摘要后再批准。
5. 再次失败时保留现场并反馈，不反复点击或重新提交同一操作。

恢复审批会先展示需要你决定的内容：保留哪些开发进度、哪些异常环境仅留在历史现场，以及
批准后要经过哪些验收。Task ID、源码版本摘要、原执行证明等放在“技术核对信息”中，供工程
人员排障；不需要产品使用者手工填写。

“保留开发进度，继续原需求”仍接续当前需求。已经终止的旧执行保留为历史记录，平台按批准的
方案安排新的内部执行任务，不会在需求列表创建同名需求。只有当前方案完成核验后才可批准；
来源事实或工程输入发生变化时需要重新检查。工程确认不能代替后续独立 QA 和 Reviewer 验收。

Reviewer 中断后，平台依据已封存的 QA 证据决定是否只恢复 Reviewer；页面处于 REVIEW
不代表模型仍在线，也不代表评审已经通过。一个子仓完成后，多仓需求仍需要联合验收。

## 反馈时提供什么

- 所属 Project、需求名称或需求 ID。
- 刚才执行的操作、页面错误和大致时间。
- 页面显示的 Operation ID，以及是否已经批准恢复计划。

维护者据此查证原因，修复后会说明是否需要重启、原需求如何继续及验证范围。
合并候选与业务验收仍按团队流程执行。

设置中的重试额度修改并不一定适用于已经派发的 Task；预算耗尽、终态或旧审批问题由
[交付恢复手册](../operations/delivery-recovery.md)指导处理。不要通过改库、删除锁或清空历史恢复需求。
