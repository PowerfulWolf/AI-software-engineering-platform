# 完成维护并恢复普通模式

故障服务被安全替换后，ASE 会先进入“维护仅查看”模式。需求、任务和执行记录可以阅读，
交付和修改操作暂停。维护完成不等于需求通过，也不会自动批准或继续暂停中的 K1。

在页面顶部展开 **完成维护并恢复普通模式**，复制其中的本机命令。命令包含当前服务实际使用的
配置和状态目录，不需要寻找或删除维护文件。这是本机服务维护操作，需要在运行 ASE 的电脑上执行；
浏览器只提供指引，不向仅查看服务发送写入请求。

1. 执行第一条 `prepare-maintenance-completion`。平台先安全收尾并停止当前服务，
   核验当前停止记录、进程实际退出、完整故障归档和待执行队列。页面会暂时离线。
2. 检查终端中的方案：安全收尾、原故障关联、队列统计和 `record_sha256`。
   等待人工或依赖的工作可以保留；排队、运行、计划重试和仍有活动租约的工作需要先核实。
3. 将第二条命令中的 `PLAN_SHA256` 替换成方案的 `record_sha256`，执行
   `complete-maintenance PLAN_SHA256 --confirm-restore-normal`。平台重新核验，追加完成记录，
   再启动普通模式。刷新页面确认维护提示消失，且普通控制入口可用。

第一步失败时，平台尝试恢复仅查看服务供你查阅；终端仍返回失败并给出中文原因。
它不会清空队列、终止历史工作或替你批准需求。若提示安全收尾未完成，先查看服务状态并处理
原记录问题。若有待执行工作，应核实其实际结果和授权，使用正常受控路径处理，不要直接改库。
若提示无法读取队列，检查当前配置引用的 MySQL 是否可访问。数据库中其他项目的待执行工作
也会保守地阻止解除维护；检查覆盖该数据库的全部队列，避免漏掉执行。

确认后、首次普通启动前再次检查。方案过期时，重新运行第一步并确认新方案，旧方案与确认记录保留。
若配置显式设置了 `ASE_CONSOLE_MODE=inspection`，先取消这个环境变量，再确认普通模式。
若检查失败后只读服务也未能启动，保留终端输出和故障归档，由本机维护人员处理；不要强制删除维护标记。

本机维护锁不阻止其他独立 CLI/Worker 访问同一个数据库。执行这两步前应停止其他写入入口；
平台会在确认和首次普通启动前复查，但不会把它描述为跨进程数据库写入隔离。

全部原故障日志、生命周期、未知执行结果、需求审批和开发草稿保留。恢复普通模式后，
暂停需求仍需在需求详情中按其当前恢复或审批入口独立处理。
