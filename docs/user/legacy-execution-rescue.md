# 旧版执行中断：保留进度继续原需求

适用于“让平台处理中断”检查后仍缺少原执行结果、结束记录和完整执行前现场的旧 Coder。
这类旧执行没有可审批的普通恢复决定。重复调查不会创造缺失的历史记录。

## 操作路径

1. 在服务空闲时加载平台修复，使用 `scripts/ase-console-service.sh restart` 后刷新页面。
   新的无重启路径需要操作契约第 3 版；旧整机重启方案仍兼容第 2 版。
2. 打开原来的需求，在 Coder 等待处理区域点击“准备保留进度的恢复方案”。无需输入
   SHA、进程号或工作区路径。平台检查原调用、历史领取、剩余额度、原代码版本和全部现场。
3. 尚未在原执行后重启电脑时，平台调查当前同账户的本机 Codex 开发执行、工作区使用进程
   及可读性，并在独占任务锁和队列屏障中两次检查、封存完整合法草稿。
   有相关执行或调查不完整时显示具体等待原因、处理方和下一步；不会出现可批准计划。
4. 方案准备成功后，页面显示本机检查结果、保留进度和下一轮额度。具备工程职责的操作者
   确认原调用一直在同一电脑、同一账户本地执行，未迁移或远程；原调用及全部派生工具
   已结束且不会再修改现场；接受原结果仍未知并授权使用剩余额度另行执行。
   本机停止方案不再需要单独勾选；点击批准按钮即表示确认上述声明。只有这些事实都能确认时
   才点击。当前进程调查只是辅助检查，不能替人证明旧工具全部停止。
5. 点击“批准保留进度并继续原需求”。平台记录精确决定，保留原需求、分支、工作区和历史，
   使用剩余工作额度建立下一轮真实执行。后续仍经过独立 QA 和 Review。

不要求为停止空闲 ASE 或准备此方案而重启整台电脑。无法确认旧调用和派生工具已结束时，
不要点击批准；由工程维护核实原执行，或保存其他工作后重启原执行所在的整台电脑。
平台观察到原执行之后的真实整机启动时，会沿用旧的同机重启方案，审批明确显示对应声明。

原中断轮次的结果继续记为“未知”。新的救援记录不是原调用成功、停止记录、Coder 进度
或验收通过证明；不会退款、重置次数或虚构供应商故障。无需删除或重建需求。

## 检查不通过时

如果页面显示“完整草稿暂时无法封存”或“保留草稿捕获失败”，平台在保存开发进度时拒绝了
某项文件校验。这与旧执行是否停止是不同检查。查看当前恢复检查和复制报告里的具体错误操作，
由平台维护者核对文件格式、权限或敏感信息分类；处理后点击“修复后重新检查恢复前提”。
原文件保持，不需要为了绕过检查而修改草稿或重新创建需求。后续调查不会覆盖这次准备失败。

- 当前本机执行或工作区使用仍存在：等待结束，或通过原入口正常停止，再点击重新检查恢复前提。
  ASE 服务和在另一代码目录维护平台的 Codex 会话可以保持在线；普通空闲终端仅停留在
  原工作区目录也不要求关闭。平台不会把 Codex 框架或辅助程序的目录名当成开发执行。
  如果交互 Codex 就在原 Coder 工作区内，或者还有 Python/Node、运行命令的 shell 等工具
  留在那里，以及任何工具仍打开原工作区文件，仍需通过原入口正常停止后再检查。
  不要通过结束当前维护会话来绕过检查；本机调查通过后仍须如实确认旧执行及派生工具已结束。
- 当前账户进程读取不完整或调查能力不可用：平台维护者修复查询能力，再检查；不得假报停止。
- 已找回原执行的真实最终结果：使用原结果检查与接纳路径，不以救援覆盖结果。
- 现场包含未纳入完整草稿的忽略文件、受保护规则、链接或权限外改动：平台保留文件并拒绝
  直接启动。需工程维护按具体拒绝原因检查现场；不要清空工作区来绕过检查。
- 工作额度耗尽或原领取/规范资料缺失：救援不会新增授权或预算，应按平台显示的具体事项处理。
- 尚未批准的方案封存后现场或输入发生变化：点击“重新准备恢复方案”，再确认新方案。
- 平台已保存工程批准及恢复绑定，但队列尚未完成时：再次准备会找回原方案，重试原批准即可；
  同机后来再次整机重启不会重新消耗额度。如果完整现场此时已经变化，平台保留文件并拒绝
  启动，需要工程维护检查；不能用新方案绕过已保存的决定。

旧工程处理报告作为历史完整保留。当前操作入口及新工程决定在执行记录中可查看。

## 回滚

尚未写入新增本机调查/声明记录时，可受控停止服务后回滚代码。已经写入新版 method/证据/绑定时，
保留兼容读取这些事实的版本并向前修复；不能部署无法读取新记录的旧服务，也不能删除
审计或工作现场来回滚。
