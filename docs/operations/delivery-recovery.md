# 平台操作与问题反馈闭环

本页保存通用操作与交接方法。具体需求、checkpoint、失败现场和当时的恢复步骤见
[2026-09-18 事故归档](../archive/2026-09-18-console-recovery-incidents.md)；归档中的旧步骤需要结合
后续更正阅读，不能直接套用到其他需求。

## 分工与交接

- 用户在 Web Console 创建需求、审批范围/计划、继续交付和验收结果。
- 开发协作者按需求 ID、操作、错误和时间读取对应 Operation、Task、运行证据及规范，定位问题。
- 修复使用最小复现、fake adapter 和相关回归测试，按变更范围完成必要质量门；真实模型交付由用户在平台继续执行。
- 交接说明原因、改动、验证结果、是否重启、现有需求的下一步及回滚方式。
- 涉及持久化事实时单列存量数据处置，保留历史，不通过改库模拟审批或重置终态 Task。
- 用户继续操作，下一处异常进入同一反馈闭环。

## 控制排查和验证成本

- 聚焦当前阻塞，按 ID/时间定位日志和规范章节，避免重复收集全仓上下文。
- 必要检查通过后交回操作，不为观察交付而持续轮询或重复真实模型链。
- 验证范围由风险和项目质量门决定；新增失败或跨层影响才扩大检查，不跳过所需独立 QA/Review 或伪造 verdict。
- 操作处理完成不等于交付完成，需检查实际阶段与阻塞原因。

## Reviewer 中断

1. 在状态页确认 Reviewer 的实际主模型和备用路由。
2. 在原需求点击一次“继续交付”，查看返回的操作结果。
3. 若返回候选验证计划，核对候选与摘要后批准。已开始但未封存结果的旧调用，需要新的精确计划和审批。
4. 原候选已有终态事件引用的 sealed QA PASS 时，恢复仅执行独立 Reviewer；没有有效 QA PASS 时执行 QA → Reviewer。发现代码缺陷才进入 Coder 修复。
5. 再次失败时保留需求/Operation ID、错误和时间，交由排查，不重复点击。

未封存验证结果不等同于 Review REJECT。额度恢复也不等于调用自动恢复；
UNKNOWN_EXIT 只能证明进程失败，不能单独证明额度原因。

## Coder 尚未启动就因上下文超限阻塞

这类失败通常只有 `NEW → PLANNING → BLOCKED`，没有 Coder Run、修改或候选。
“无法确认 Coder 身份”在这里是旧恢复入口错误分类，不是又发生了一次 token 超限。
修复预算/上下文策略后，旧 Task 仍保持终态，不能直接清零或改库重新运行。

1. 应用支持 `pre_execution_restart` 的版本并重启服务。
2. 在**原需求**点“继续交付”，或运行 `ase request resume <需求ID>`。
3. 核对“批准 Coder 启动前重启”的原任务、基线、目标分支和预算，再点“批准并继续”。
   CLI 使用刚返回的 `restart_plan.plan_sha256`：
   `ase request resume <需求ID> --approve-plan <摘要> --approval-reference <批准说明>`。
4. 新 Task 接回同一需求，仍需独立 Coder → QA → Reviewer；原审批、失败 Task 和事件保留。
   不需要删除需求、重做 Product 讨论，也不会把没有实现过的内容交给 QA。
5. 若提示已有工作区/上下文/角色执行记录，停止自动重启并核对事实；不删除现场来强行满足
   条件。若页面显示“准备资料在首个角色执行前漂移”，平台会生成
   `restart_kind=preparation_rebind` 的新精确计划：它绑定当前准备摘要/基线，只有在原 Task
   仍为 NEW、没有事件、调用、claim 或工作区时才可批准。批准后平台创建追加 successor，再进入
   Coder → QA → Reviewer；Manager 不能把旧 dispatch 直接当成功。新 Task 再次在上下文阶段失败时，
   不自动无限创建 Task。

**存量数据处置**：无需改库或迁移旧 journal。K1 自动知识采集首个闭环（需求
`delivery_multi_33d30fe0776a232e31617caa9e702b915dcb4c65`，原 Task
`task_f887a81a33cfe89bdafd24ea01ab5ca8`）已只读核验符合初始失败条件，原代码基线未变。
本次修复不替用户批准新计划、不执行此需求；部署后按上述步骤生成并审核新的精确摘要。
普通“继续”授权不能代替尚未生成的计划审批。

代码回滚可撤销本次提交；一旦写入新的 restart plan/dispatch，旧版本不能解释该 kind，
不要让旧服务继续推进这些 Task。保留新兼容读取器并前向修复，不删除新记录或重写旧哈希。

## 子仓已完成而父需求未完成

父需求阶段、角色队列、角色占用和候选验收是不同事实。先核实 child 的原生 journal、
候选和封存证据，不因父页面仍显示实现就重新启动 Coder。

单仓需求复核既有完整验收项、QA PASS、Reviewer APPROVE 和精确候选，封存
SingleRepositoryAcceptance 后完成父需求。不会再跑联合 Planner/验收，也不重置旧 integration 次数。
即使父需求处于 PLANNING 且 plan 为空，也必须从同一父 journal 找回原批准计划，只读重建验证上下文；
证据缺失或漂移时保持失败，不手工改为 DONE。

多仓需求还必须完成候选集合的联合验收。命令无法启动、超时、零测试或非零退出时保留 integration
evidence；已完成子仓库的 QA/Review 不因此失效。继续操作按当前事实触发有界重规划，只有命令策略
和验收覆盖通过才再执行。预算耗尽时若平台返回补充验收计划，必须核对并显式批准，旧失败与预算历史保留。

## 恢复与回滚边界

- 沿用原 MySQL 和平台数据根，通过当前页面/CLI 给出的精确范围及计划审批继续。
- 代码回滚与数据回滚分开判断；旧服务不认识的新审批字段不能被旧版本继续写入。
- 每次修复单独核对现有需求是否需要操作，测试结果不能替代真实候选验收或用户审批。

## Design 预算耗尽与存量需求处置

Design 的设计尝试与临时故障现已分开计数，默认分别为 3 和 5，可在“设置 → 通用设置 → 执行与
重试策略 → Designer”调整（1–100）。`joint design attempt budget exhausted` 指设计尝试耗尽；
`joint design transient failure budget exhausted` 指临时故障耗尽。两者都在模型调用前拒绝继续。
504 是供应商/网关返回的临时错误，发生在知识咨询时也只消费新的临时故障额度。

处理 Designer 预算耗尽时，先查看原需求提供的操作：

1. 若页面显示“恢复设计”，核对原需求与历史知识批准，通过该入口恢复；
   它只适用于平台能验证的历史断点，不应手工给其他需求补造恢复条件。
2. 临时故障先核对模型服务，再根据需要调整 Designer 的临时故障上限；
   工作预算不足时调整设计尝试上限。保存并应用配置后再继续，计数不会清零。
3. 没有可用恢复入口的旧需求按其当前错误和冻结策略处理，不直接修改 checkpoint。

具体旧需求、2026-09-22 的断点与当时操作保存在
[恢复记录原文](../archive/2026-09-28-delivery-recovery-source.md#design-预算耗尽与存量需求处置)。

Product/Planner 耗尽同样先核对错误，再提高该角色对应上限、应用配置并继续；原对话、审批和计数保留。
交付 Task 的策略在首次 dispatch 时冻结。已存在 Task 不会因为调整全局配置获得额外授权；
若已 BLOCKED，打开原需求点击“继续交付”，检查平台生成的恢复范围/计划，按页面要求精确批准，
再继续执行。候选复核或 Coder 恢复由现有 durable facts 决定，不能通过改库强制选择。新恢复 Task
保留原冻结策略但开始新计数；原 Task/失败历史不变。没有策略字段的旧 Task 仍按原 max_attempts。

版本回退前先停止运行操作，并核对目标版本是否支持已经产生的策略和历史记录。
已经产生 `Task.retry_policy/retry_failures` 或超过 10 的执行身份时，旧二进制可能无法读取，
应保留兼容读取器并前向修复；不能删字段、重写哈希或清空数据库来降级。
历史 `design_retry_policy` 向全角色策略迁移的当次回退说明保存在上述原文快照中，
必须按确切版本及实际数据重新判断适用性。
