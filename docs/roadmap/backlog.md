## 目标与已有基础

目标是 **Trellis 式工作流与规范沉淀 + 独立多角色交付 + 可检索的组织知识**：每次需求产生可验证经验，
经治理后进入组织记忆，后续会话按项目、角色、阶段获得足够背景；能力提升也经过独立验证，而不是 Agent 自我批准。

以下能力已经存在，不能再当作从零建设的待办：

- Coder、QA、Reviewer 独立身份、Run、Context、worktree，同一候选的测试/评审和证据完整性校验。
- typed tools、路径/命令策略，以及已接入 Swift/UI 能力的版本化执行器、隔离边界和精确审批。
  不同执行器的具体隔离方式不同，不能据此宣称任意新工具已经获得同等保障。
- 中断恢复、候选复核、关联修复；符合精确证据条件并重新批准后，独立 QA PASS 可保留、仅恢复 Reviewer。
- Manager 候选验证的 incident、当前探测、精确提案/审批、受控执行 receipt、独立验收和恢复链。
- 知识/Spec 分离、冻结快照、角色检索引用；三类交付报告的证据化发现、显式收集、待审发布及前端来源展示。
  已批准的知识解答还有独立的提案来源协议；批准解答不等于批准长期发布。
- 一次真实需求已由 ASE 正常完成至 DONE。历史中断保留；Mock UI 证据不代表真实 OAuth 验收。

### 四类信息不能混用

| 类别 | 例子 | 正确归属与处理 |
|---|---|---|
| 项目背景知识 | 某模块的依赖、某项目 XCTest 需要完整 Xcode | 带来源和适用范围的知识提案，审核后供未来需求检索 |
| 强制规范 | 不允许修改生产库、候选必须具备哪些验证证据 | 显式审批、版本化启用的 Spec，不从模型笔记自动升级 |
| 当次环境状态 | 桌面锁定、Xcode 未安装、MySQL 停止、上游 504 | Manager 的前提/incident；协调、重新探测、恢复，不直接变成全局规则 |
| 可执行能力 | Swift 测试、UI 驱动、未来 Maven 执行器 | 受控工具/执行器的实现、验证和版本化授权；知识不能授予执行权限 |

## 角色责任

下表是演进目标中的职责分工；未接入的经验生产者见 K2，未统一的前提协调见 M1。

| 角色/组件 | 应承担的责任 | 不可越过的边界 |
|---|---|---|
| Manager | 识别缺口、提出方案、协调已有能力或人、跟进解除并恢复；提炼可复用协调经验 | 不代写业务代码/验收结论，不把自由文本建议当授权 |
| Product | 明确业务语义与验收条件，提出可复用业务事实 | 不自批 ProductSpec，不把推测当事实 |
| Designer / Planner | 记录技术决策、依赖、风险、能力需求及有证据的经验 | 不因方案需要就自行扩权；规划不代替实际派发校验 |
| Coder | 使用项目上下文实现需求，提交带证据的发现 | 不批准自己的代码，不改 QA/Review verdict 或平台 policy |
| QA / Reviewer | 独立验证同候选，审查证据并提出失败模式/可复用发现 | 未执行不能记 PASS；Reviewer 不修源码或自行 merge |
| Knowledge Plane | 提案、审核、发布、选择、冻结、检索引用、失效治理 | 不把任意聊天记录自动变强制规则，不追改历史上下文 |
| 确定性服务/执行器 | 强制检查权限、身份、租约、幂等和版本，封存真实执行证据 | 自然语言不能覆盖机器权限、凭证和审批边界 |
| 人或明确授权的审批方 | 核对精确计划、业务事实和权限范围，处理必须人工介入的环境动作 | 审批不等于测试通过，不替代独立验收 |

## K1 自动知识收集闭环

**现状：** `ProjectLearningStore.collect` 已收 QA/Review 失败及 Coder/QA/Reviewer 的 `project_observations`，
生产入口由显式收集调用。尚无每个 accepted checkpoint 的可靠自动触发、持久增量游标和失败补偿。

**责任/范围：** 平台 Learning 服务负责可靠收集；角色只提交证据化发现；发布仍经精确审批。
主要涉及 `learning.py`、artifact/checkpoint 接纳处、持久调度边界和 Console 学习页。

- [ ] 定义采集事件与稳定身份：绑定 Team/Project/Repository、Task/Run、角色、artifact ID/SHA、revision 和 observation ID；只消费已封存、可重验的来源。
- [ ] 在事实接纳之后登记可恢复的采集工作；明确事实已写入、采集尚未登记时如何对账补偿，避免只有进程内回调。
- [ ] 增加有界批次、持久游标、幂等去重、失败原因和显式重试；复用已有持久机制，不为此引入外部消息队列。
- [ ] 自动入口与显式 collect 共用提案身份和服务；重复触发、并发、重启或历史补采不生成重复提案，也不覆盖已有审批。
- [ ] 失败只影响采集状态，不改交付 verdict、不阻塞已经合法接纳的报告；不得自动发布或启用任何知识/Spec。
- [ ] 为旧数据提供有界、可审计的补采路径：无 observations 的历史报告不能凭模型回忆补造发现。
- [ ] 补齐采集开关和停用语义；关闭自动触发后保留提案、决策、游标和审计历史，显式入口仍可用。

**完成标准：** 需求 A 接纳报告后自动形成待审提案；故障注入覆盖接纳/登记/发布之间的中断，重启后无漏收、无重复。
未经批准不可检索；批准发布并选择后，新需求 B 可检索并引用该知识，A 的冻结快照不变。
正常成功报告、失败报告、空发现、损坏来源和跨 Project 来源都有正/负例；GET 页面不触发采集写入。

**最小闭环：** 先覆盖现有三类交付报告，不等待所有角色协议完成；K2 的来源随后接入同一生命周期。

## K2 上游与 Manager 的经验生产者

**现状：** 正常 Coder/QA/Reviewer 已能提交 observations，已批准的知识解答也能形成提案。
缺口是 Product、Designer、Planner 与 Manager 的前提协调经验没有统一、完整的生产/采集协议。

**责任/依赖：** 各角色对来源与适用条件负责，Learning 服务校验；与 K1 共用收集接口，不另建一份知识库。

- [ ] Product 记录已确认的业务术语、约束和澄清结论；Designer 记录技术决策与取舍；Planner 记录依赖/计划经验，保留各自真实来源身份。
- [ ] Manager 从 incident、方案、执行 receipt、重新探测及最终恢复结果提炼候选经验；没有角色报告时用专门 typed 来源，不能伪造 QA artifact。
- [ ] 每类提案明确来源 revision/摘要、owner、证据、适用项目/角色/阶段和长期适用条件；支持没有可沉淀内容。
- [ ] 区分“事实”“建议”“尚待验证的假设”；解锁了一次桌面只记录当次状态，项目工具链要求可申请成为限定范围的知识。
- [ ] Python、JSON Schema、模型传输、持久化、发布重验、前端来源文案和未来检索同步更新；旧字段缺失时保持原 hash。
- [ ] 沿用待审/拒绝/发布流程；一次恢复批准不得复用为长期 Spec 启用或能力安装批准。

**完成标准：** 每个新增生产者至少有一个贯穿来源→采集→审批→前端→后续需求检索的用例；缺证据、来源漂移、跨项目、重复采集均被正确处理。
能具体回答“这条经验从哪个角色、哪个需求、哪项证据来”，而不是只显示一段模型总结。

## K3 知识闭环的前端、效果与失效治理

**现状：** 已有知识资产、提案来源/适用范围/决策展示、冻结快照、检索引用和部分效果测试。
要补的是自动采集运营状态、跨需求使用追踪和完整维护闭环，不是重新做上传页。

**责任/依赖：** Knowledge/Learning 服务提供可验证状态，Console 只展示；K1 提供采集进度，K2 提供更多来源。

- [ ] 展示待采集/处理中/采集失败及重试、待审/拒绝/发布、启用/替换/退休，并与索引 READY/FAILED 状态区分。
- [ ] 提供提案→发布版本→启用集合→冻结快照→具体角色检索/引用的来源链；保留当前项目切换和 scope 一致性约束。
- [ ] 记录实际检索和引用，而不把“注入 Context”“模型读到”“实际采用”“验收有效”视为同一件事；无证据显示未知。
- [ ] 定义知识冲突、过期、源代码变化的复核与替换/退休流程；停用只影响未来选择，不改旧快照和历史 verdict。
- [ ] 建立可比较场景，观察重复追问、返工和失效知识误导；记录项目/模型/任务差异，不把所有改善都归因于知识。
- [ ] 为预算有限的会话保留 required policy/验收/证据，按 scope 检索相关知识；禁止通过全库灌入或截断必需证据解决上下文不足。

**完成标准：** 前端能定位一条知识的来源、状态、使用者和替代版本；展示失败重试与无引用情况，权限过滤覆盖标题、元数据和正文。
同项目需求 A→B 的复用测试、不同项目隔离测试、失效停用后的新旧快照测试均通过。

## M1 Manager 全阶段前提协调

**现状：** 候选验证已接通 incident→当前 probe→精确方案/审批→受控执行→receipt→独立验收/恢复。
尚未统一覆盖 Product/Design/Planning/Coder 的环境、数据、权限与能力缺口。

**责任：** Manager 对“谁来解决、何时解除、如何继续”负责；确定性服务校验/执行，必须人处理的动作由人完成。
不要求 Manager 自己安装所有依赖或拥有无限 shell 权限。

- [ ] 统一缺口分类及阶段绑定：区分环境、数据、授权、知识、执行能力、业务歧义和真实代码缺陷，保留现有知识 Gap 协议。
- [ ] 每个 incident 绑定受影响阶段、原 checkpoint、事实来源、协助方、解除条件、允许的探测和下一安全动作。
- [ ] 各阶段先检查可确定的前提；执行器在模型启动前失败也上报 Manager，不能只监听 QA 报告。
- [ ] 能由已有获批能力处理时提出精确计划；缺能力时进入能力提案，必须人工介入时明确请求，不把“用户说修好了”当探测成功。
- [ ] 等待时释放 Lease/容量并保留工作；重复未变化前提不消耗无意义的模型/验收重试，调度等待与 Task 交付状态保持分离。
- [ ] 前提变化后重新探测、更新建议，按当前 candidate/范围/策略重新批准必要执行；不重放 consumed approval，不重跑已接纳阶段。
- [ ] 让 Console、CLI、正常/修复/恢复路径调用同一协调服务，避免只有孤立 Manager 类能处理、生产入口没接入。
- [ ] 输出限定范围的可复用经验供 K2 收集；环境状态不直接升级成强制 Spec。

**完成标准：** 对每个新增阶段模拟不可用→等待→重启→解除→重新探测→恢复，验证无重复副作用、无 Lease 泄漏、旧记录可读。
至少覆盖缺工具链、桌面锁定、测试数据缺失、无权限、数据库不可达；同一错误不会被误派 Coder 改业务代码。
测试环境不可用时给出明确未验收范围，不能用假 PASS 关闭阻塞。

## Q1 生产组合回归矩阵常态化

**现状：** 已有大量 Git/MySQL、历史兼容、CLI/GUI 与恢复回归；真实工具链和桌面等 opt-in 套件不保证每次执行。
本次修复暴露的问题主要在组合入口，单模块通过不能证明生产链路可用。

**责任：** 平台测试工程维护可重复矩阵，独立检查确认覆盖；不以运行耗时为由合并“跳过”和“通过”。

- [ ] 快速层固定运行 Python 离线契约、Node 前端、类型/格式/构建；数据库层使用独立、受保护命名的 MySQL 测试库。
- [ ] 环境层分别声明 CLI、Swift/XCTest、桌面 UI 的前提、显式开关和证据产物；执行前探测，不默认访问真实账号/生产数据。
- [ ] 固定覆盖 Console/CLI 与正常/修复/恢复的组合入口，fresh Host、旧记录升级、多候选、多次中断、QA PASS 后 Reviewer-only、已完成 checkpoint 接管。
- [ ] 覆盖等待/心跳竞争、租约过期、相同操作重复提交、旧批准/来源漂移拒绝，以及大上下文、慢 stdin、不同模型路由。
- [ ] 验证真实执行边界的拒绝行为：越权文件、命令、网络、环境变量、路径别名；普通 subprocess 测试不能替代隔离执行测试。
- [ ] 将修复回归绑定 failure mode 和 spec；记录每层版本、环境、耗时、通过/跳过/排除/失败，不拼接多轮结果冒充单次全量通过。
- [ ] 给现有 sidecar 历史构建脱敏 fixture，保证不靠直接改生产记录才能恢复。

**完成标准：** CI/runbook 可重现矩阵，失败可定位到具体入口和不变量；同一组合 bug 的回归随修复进入固定执行层。
至少有真实平台入口完成到 DONE 的验收，且验收人员不代写候选、不伪造 verdict。

## C1 统一的新能力接入、验证与发布

**现状：** 隔离执行、独立 QA/Reviewer、精确执行计划与 Swift/UI 适配已存在。
`SKILL` learning 发布目前只写设计提案，**不会安装、注册或启用可执行能力**。

**时序/责任：** 自动知识闭环之后推进。Manager/Planner 提出能力需要；能力实现者开发，独立验证/评审者验收，
授权方批准启用，确定性 registry/executor 执行权限。平台维护与业务需求实现分开，不由需求 Agent 自行修改平台安全边界。

- [ ] 定义版本化能力描述：稳定身份/版本/摘要、输入输出契约、适用角色/项目/阶段、工具链前提、允许路径/命令/网络、超时预算及 evidence 格式。
- [ ] 定义发现接口，让 Manager/Planner 能区分已存在、环境未就绪、尚未授权和需要新增的能力；能发现不等于能调用。
- [ ] 将提案与实现、测试证据、独立评审关联；复用现有隔离 worktree/执行与 QA/Reviewer 机制，不创建绕过原门禁的发布捷径。
- [ ] 最小样例可选 Maven 等新执行器，项目选择另行确认；同时验收允许操作可完成、越权操作必拒绝、前提失败可交给 Manager。
- [ ] 增加版本化注册与启用协议：限定角色/项目/动作，人工或预先明确授权的策略批准，运行固定到精确版本和权限摘要。
- [ ] 设计已批准计划遇到能力版本变化的失效/重提案条件；历史计划、receipt 和已运行记录不可被新版本静默重解释。
- [ ] 提供停用、回退和在途任务处置；保留旧版本与证据，撤销后禁止新的未授权启动，不用删除历史实现“回滚”。
- [ ] 记录运行反馈、拒绝/失败率和兼容性；新增实现代码的回滚与已发放权限的撤销分别处理。

**完成标准：** 一个新能力完成提案→隔离实现/测试→独立评审→精确启用→Manager 发现并使用→停用/回退；
可追溯“谁在什么授权下用了哪个版本”。无授权、越权、旧批准、损坏包或不匹配前提均不能运行。
Agent 不能通过修改文档、Skill 提案或 prompt 给自己新增执行权。

## S1 其余 CLI 角色执行权限审计

**现状：** 独立 QA/Reviewer 已采用 no-command/只读 CLI，测试由精确计划的执行器供给真实 receipt。
其他 CLI 角色与 Responses typed-tool 入口的实际能力一致性仍需逐一核查。

- [ ] 列出 Product/Designer/Planner/Coder 等角色实际可见的工具目录、读写路径、命令、网络及环境变量，而不是只审 prompt。
- [ ] 将正常、恢复、修复和知识查询 Run 的 policy 与角色绑定核对，覆盖工具别名、路径别名、子进程和跨 Task 数据访问。
- [ ] 对拒绝行为做真实后端验证，输出脱敏 evidence；区分 CLI 宿主机制与平台 typed tools 的保障范围。
- [ ] 对缺口实施最小权限修复，回归正常工作路径和旧计划兼容；不为了通过审计统一关闭必要能力。

**完成标准：** 角色×后端权限矩阵有实际命令/文件拒绝证据；不一致项已修复或有明确阻止执行的边界。
责任归平台 policy/adapter 维护者，不能让角色自行宣称“我不会越权”作为验收。

## P1 刷新与投影性能预算

**现状：** 历史验证图指数重验、刷新忙时丢项目切换、Knowledge 内容/身份错位已修复。
本次现场仍曾观察到单 GET 约 7.4–8.0 秒，这是待优化的观测，不是固定性能结论。

- [ ] 为 MySQL 查询、sidecar 读取/重验、图遍历、投影和前端渲染分别计时，构建随需求量/历史深度增长的基准。
- [ ] 基于基准确定请求/交互耗时预算与回归阈值；先测量再决定索引、分页或投影优化，不预设全局缓存。
- [ ] 优化保持单次请求内已完整验证节点的复用，后续请求仍重验可变来源，禁止跨请求缓存陈旧“可信”结论。
- [ ] 压测慢响应下快速切换、自动刷新、失败重试和交付按钮；保留 latest-intent、旧响应拒绝、scope 一致与 GET 只读。

**完成标准：** 同一数据集有可比较的前后结果和增长曲线；延迟降低且新篡改能及时被拒绝，慢接口也不丢用户选择。
责任归 read projection/Console，不通过减少审批或来源校验“提速”。

## R1 模型路由健康与 Manager 诊断

**现状：** 已有每角色授权 fallback、typed 错误和实际路由记录；上游多次 504 仍会拉长交付。
上游故障不是 ASE 代码缺陷，无界重试、错误归类或不可恢复才是平台问题。

- [ ] 按实际路由归集脱敏的失败类型、延迟和时间窗口，区分额度、认证、网络、上游故障、无效输出和策略拒绝。
- [ ] Manager 提供当前证据及可执行建议，必要时请求人调整配置；评估有界健康探测/冷却，避免把探测变成无限付费调用。
- [ ] fallback 只在该角色既有授权路由内发生，不因“可用模型池有它”就新增目的地；目的地或权限改变仍走配置/审批边界。
- [ ] 验证故障→等待/回退→恢复与计数预算、checkpoint、真实选中模型的一致性；未知调用结果不重复执行。

**完成标准：** 可解释一次交付为何等待、用了哪条路由、下一步谁处理；持续故障不会耗尽无意义重试或泄露上游凭证。

**完成标准：** warning 对应问题有针对性回归；凭证迁移可回退且不泄漏，服务重启后访问同一受校验 workspace。
系统凭证库和自动启动按实际运维需求单独立项，不阻塞 K1。

## F1 暂缓或需独立决策的事项

- [ ] **Reporter/T033**：先确认用户需要何种交付表达，再决定确定性服务还是独立 Agent；不能从现有 Evaluation/Handoff 推断已接入日常交付。
