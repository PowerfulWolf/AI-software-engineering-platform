# ASE 交付方向与恢复复杂度复盘

日期：2026-10-04。范围：首个 bootstrap 的目标、现行 README/ADR/工作流、v0.1.2 之后的修复演进、当前 K1 的真实事实与本次路径/权限修复。本文是有来源的方向评估与实现复盘，**不等于全仓审计或零 Bug 证明**。本轮已按后续方案落地第一切片，并保留明确的能力边界。

## 判断

ASE 的核心目标仍正确，独立角色、可验证证据、不可自我批准、组织知识和隔离工作区应保留。当前正常路径没有跳过 Coder → QA → Reviewer，也没有用 root 修业务代码替代 ASE 验收。

但正常交付的可用性没有跟上安全机制：许多可处理的技术中断先被压成 Task 终态，再通过特殊恢复计划、successor Task、人工审批和 read-side 补偿接续。**这种状态与职责分散带来的复杂度不应成为长期产品形态。** 用户在操作中被迫理解平台内部的 Run、lease、hash、基线和恢复分支。继续逐个添加历史特例，会保持当前局部正确，却让整体行为越来越难预测。

本次局部修复是防止误改业务模块和组织规范、保全存量需求所必需的补救；它增加的 quarantine 只读审计路径不是未来日常交付的推荐模式。本轮已收敛恢复、状态和删除契约；现有 K1 按用户最新指示正式删除，不以重建 Requirement 代替可靠性建设。

## 初衷与合理演进

初始 `6138cb1:README.md` 明确目标：已有 Git 项目 + 一条可验收需求，经串行 Coder、独立 QA、独立 Reviewer，产出可合并变更或明确阻塞证据。三个原则分别是组织拥有知识、角色不得自我裁决、角色通过可核验 artifact 交接。初始边界禁止复杂 DAG、自动合并保护分支和自动生产部署。

现行 `docs/decisions/0002-organization-owned-agent-workforce.md` 与 `docs/architecture/overview.md` 接受了 Team 拥有长期成员、Project/Repository 外置 sidecar、Product/Design/Plan 上游、持久队列及联合需求等演进。这些已接受的职责不应因为早期 README 更窄就一概撤销；它们服务于“组织化软件工程团队”，单 Task 串行、独立验收与证据边界仍须保持。

理想使用流程应是：选择项目和代码目录 → 澄清并批准产品需求 → ASE 计划/实现 → QA 测试、失败回 Coder → Review、驳回回 Coder → 领取候选、报告与完整历史。平台应处理权限内的技术重试，用户处理业务决策、真实授权变化和不能自动解决的前提。用户不应手工决定该用哪种恢复入口或查数据库判断谁在运行。

## 当前实现的证据与问题

### 保留价值的变化

- Task/Run/Artifact 的身份、revision、证据和 digest 校验阻止错误候选成为 DONE；原失败历史不因恢复被覆盖。
- 真实 claim、owner fence、lease 释放与角色工作区隔离解决了进程重启和并发所有权问题；不能删除这些保护来降低阻塞数字。
- 实际路由与分配模型、执行存活与交付 checkpoint 已分开表示；完整 QA/Review finding 与修改 lineage 应持续展示。
- 原生路径身份、冻结上下文、预算事实、中文诊断等修复是真实缺陷修正，不能全盘回退。

### 改造前已偏离正常产品体验的部分

1. **原因与处理混用。** `agents/codex_cli.py` 的 timed-out/failed 且 dirty 路径统一返回 `POLICY_VIOLATION`。有 dirty 只能证明存在未接纳改动，不能单独证明越权。当前 K1 确有规范改动，需要拒绝复用；其他合法 dirty 中断也被相同类别停止，容易误导 Manager 和 UI。
2. **可等待的执行问题被终态化。** `orchestration/retry.py::_blocked` 把知识失败、本地窗口耗尽、部分平台异常转成终态 Task。ADR 已要求 WorkItem 的等待/重试与 Task 的交付 checkpoint 正交。底层历史兼容行为仍使许多恢复只能追加新 Task，恢复入口因此持续增长。
3. **恢复决策分散。** `recovery/resume.py` 中先后处理上游重试、未执行重启、候选验证、前提修复、知识等待、Coder 恢复和中断恢复。每种证据都值得保留，但“该继续哪一步”的判断不应重复散落在 Controller、NativeReader、backend、Manager 和 projection 中。
4. **UI 被迫补偿事实迟到。** `team_view/reader.py` 需要发现尚未回接父 checkpoint 的 live successor，以免需求仍显示 BLOCKED。读取补偿对旧数据有价值，但不能长期承担第二套交付状态机；新的 dispatch/运行事实应及时提交明确的当前交付游标。
5. **基线与运行版本容易混淆。** 本项目同时是 ASE 控制平面和被 ASE 开发的目标仓库。更新平台服务与更新业务候选源码不是同一操作。因为每次修平台都推进目标 main，再强制恢复冻结 Task，单个需求不断遇到新的兼容组合。
6. **规划与实际工作窗口不匹配。** 当前 K1 冻结了 53 个允许路径，草稿只完成其中部分内容；Coder 在 1800 秒本地上限被停止，没有合法 progress/report。上游计划不应只产出一个大范围清单，还应按可完成步骤、验收映射和 checkpoint 窗口安排串行工作。

复杂度信号：相对 `v0.1.2`，本轮修复前的 `ff91c78` 有 64 个提交，452 个文件变化，新增 31,921 行；其中 source 9,872、tests 10,381、docs/Trellis 7,841 行。恢复模块从 26 个文件增至 35 个，`resume.py` 从 757 行增至 1,029 行。数字本身不能证明设计坏，但结合反复相同类型中断，说明现在需要收敛而非继续扩大旁路。9 月 28 日的交付复盘已经指出“正常/恢复/历史/真实执行器的契约未统一接通”；本轮说明这个问题还未完全解决。

## 哪些阻塞合理，哪些属于平台责任

| 事实 | 合理处理 | 用户是否必须介入 |
|---|---|---|
| QA 有效 FAIL、Review 有效 REJECT | 封存 finding，串行路由给同一需求的 Coder 返工，完整显示轮次 | 通常不需要 |
| 已授权范围内 typed provider transient | 保存事实、新 Run、新 claim，在预算内自动重试 | 通常不需要 |
| 本地执行窗口到期且有合法 progress | 同 Task/branch 按 checkpoint 继续 | 通常不需要 |
| dirty 但无合法报告的中断 | 保留现场，验证路径/HEAD/claim/授权，给出受控恢复决定；不当成候选 | 取决于是否改变授权；不能一律称为越权 |
| 业务歧义、范围/权限扩大、新代码基线、预算追加 | 展示具体差异，记录精确授权或知识 resolution | 需要授权者，已明确委托可代处理 |
| 执行器前提缺失 | Manager 先探测、提出精确方案，真实执行与独立验收 | 只有方案需新权限或外部动作时 |
| 缺证据、source 漂移、受保护文件变更、无法证明执行已停止 | fail closed，保留历史，给出可操作原因 | 安全停止正确；无恢复指引仍是平台缺口 |
| 平台误分类、丢掉 finding、显示假运行、审批自行过期 | 平台缺陷；修复并处理存量 | 不应让用户反复重建需求规避 |

Manager 可以在既有用户授权和确定性 policy 内调用继续/重试 Skill。它不能因“我判断安全”就自批 Product、放宽路径、覆盖 QA/Review 或把未完成代码认定通过。技术恢复自动化应来自可执行授权规则，而非让模型充当审批机关。

## 收敛方向与最小实施顺序

1. **定义统一执行事实与恢复决定。** 以“是否 admission、是否真实调用、是否有合法 progress/candidate/verdict、是否仍持有 claim、dirty 是否合规、预算和授权是否变化”构成一份 typed facts。单个纯决策入口输出继续、自动重试、返工、等待授权或终止；Controller 执行决定，Manager解释/协调，UI 展示相同原因。不能继续每报一种异常就增加一个永久 `restart_kind`。
2. **落实两个生命周期。** 新交付优先用 WorkItem 的 WAITING/RETRY 保持最近 Task checkpoint。只在无安全路径、终局预算耗尽或明确结束时终态化。旧终态不可重写，继续用经过核验的 successor 兼容；不要把兼容路径复制成新交付的默认流程。这个调整涉及状态、队列和恢复契约，必须先有明确设计与端到端负例，本文没有直接修改它们。
3. **把审批放在授权变化上。** Product 内容、source/base、范围、权限、执行能力或预算改变时审批精确差异。原授权内相同输入的重试和返工由 policy 执行。UI 显示“发生了什么、影响是什么、系统下一步做什么、需要你决定什么”，hash 作为可展开证据，不作为用户主要操作语言。
4. **分开部署版本与源码版本。** 平台服务 runtime revision、Task source revision、candidate revision 分别记录。运行引擎 Bug 修复先进入服务并重建 idle Host；仅当业务源码也需要这些修复时，通过明确的基线更新/恢复或 Coder 适配更新候选。已生成 candidate 的 QA/Review 必须验同一 SHA，不能各自追 main。
5. **规划可执行的串行 checkpoint。** 不引入 DAG，也不擅自缩减批准范围。Planner 把已批准范围映射到可验证的小步骤，Coder 到 completion reserve 前返回 progress；平台保留同 Task/branch 与完整返工理由。缺必需能力先进入前提协调，不等模型开发 30 分钟才发现测试入口或写权限不满足。
6. **验证公共交付组合，而非只验证恢复类。** 用 Console/统一入口覆盖下表。增量测试按变更范围选场景，不要求每修一次跑全量；发布全量仍由用户负责。历史兼容用明确 fixture 保留，不再用生产需求累积未知特例作唯一测试环境。

| 发布检查场景 | 必须满足 |
|---|---|
| 正常交付、两轮 QA 返工、两轮 Review 返工 | 同 Requirement、完整 finding/修改/候选历史、角色独立 |
| provider transient、本地 progress 续跑、各角色 Worker 重启 | 无丢失/重复副作用、无虚构 verdict、合法同范围续跑可完成 |
| dirty 中断、真实违规、模型预算耗尽 | 准确分类、现场保留、正确的恢复或授权门 |
| 平台服务升级、目标源码基线更新、旧 approval | 两类版本分离，真实授权变化才产生新审批，stale 安全拒绝 |
| 知识解答、候选环境修复、仅 Reviewer 恢复 | durable 人工记录、精确证据复用、不重复已经通过的工作 |
| 前端刷新/切项目/长历史/无 heartbeat | 状态源一致、未知如实显示、完整历史、不丢审批记录 |

在上述固定场景中，应要求：错误人工门为 0、未授权候选为 0、丢失历史为 0、假运行展示为 0，普通技术中断不要求重建 Requirement。“平台无 Bug”不可证明；这些可重复的交付标准能作为对外可用的门。

## 本次修复、当前存量和后续 K1

本轮修复删除恢复 proposal 的 basename 推断，生产权限编译不再授予明确 Trellis 路径；typed 写入在执行前硬拒绝规范路径（包括大小写/符号链接别名），progress/candidate 拒绝接受违规结果。原生 CLI 仍有自身 workspace sandbox 与后置校验；这不等于 OS 在写入前排除 `.trellis`，更广的 native Coder 工具权限收敛仍应单独验收。

旧 K1 恢复计划 `d9ab670f…` 与完整 122,465 字节补丁、23 个文件、失败 Task/worktree 都保留。它误把新模块 `learning_collection/audit.py` 映到 `knowledge/audit.py`，并包含 3 个规范改动，不能执行。新机制可以封存全部历史改动，精确隔离规范文件，批准 `coder_reapply` 后从干净 current base 继续；这是存量安全恢复，不是删除旧草稿或批准规范写入。

按用户要求，**当前不提交新的 K1 恢复执行审批，不启动 Coder**。两个 K1 按用户最新指示通过正式 DELETE_REQUIREMENT 退役，不创建第三个同名需求。Requirement tombstone、sealed artifact/event、历史 worktree 和审计记录保留；后续只有用户明确提出新业务需求时才创建全新身份。

重构完成后执行正式删除，不执行原 K1 恢复、不创建新需求。后续是否新建和开始业务交付，由用户再次明确决定。

本轮只执行相关增量测试与类型/格式检查。测试证明局部修复和公共组合；不代表所有平台修复完成了全量测试。真实 K1 未重新启动，两个旧需求的存量处置使用正式 DELETE_REQUIREMENT 退役，immutable 审计事实和现场保留。具体命令、结果与独立复核记录见 `.trellis/tasks/10-04-product-oriented-resumption/`。
