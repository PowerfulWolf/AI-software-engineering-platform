# Verification Role Recovery

## 1. Scope / Trigger

Use when standalone candidate verification sealed QA PASS but Reviewer did not complete, including
context construction before Reviewer admission, provider/process interruption after admission, and
successive Reviewer interruptions. This is not a new Task state or a partial verification completion.
Native `accepted_qa` still comes only from an exact terminal `QA → REVIEW / qa_passed` event.

## 2. Signatures

```python
class RetainedVerificationQa(DomainModel):
    plan_sha256: Sha256
    qa_invocation_sha256: Sha256
    reviewer_invocation_sha256: Sha256 | None = None
    qa: QaReportArtifact

CandidateVerificationPlan.reused_qa -> AcceptedQaReport | None
VerificationAdmission.reusable_qa(inputs) -> QaReportArtifact | None
FileRecoveryStore.latest_verification_attempt(task_id, *, excluding=None)
    -> CandidateVerificationPlan | None
FileRecoveryStore.validate_retained_qa(plan) -> None
select_retained_qa(store, inputs, artifacts, *, excluding=None)
    -> tuple[CandidateVerificationPlan, RetainedVerificationQa] | None
validate_retained_qa_artifacts(store, plan, artifacts) -> QaReportArtifact | None
```

`schemas/candidate-verification.schema.json` is regenerated by
`scripts/generate-verification-schema.py`. No new environment keys, DB schema or HTTP endpoints.
Normal Manager Continue → exact approval → execution remains the public workflow.

## 3. Contracts

- Source selection uses the newest platform `admitted_at`, not model-authored timestamps or the
  most favorable report. Inspect exactly that attempt; never fall back to an older PASS when a
  newer attempt has no valid QA, QA FAIL, an already sealed Review, or completed verification.
- New plan binds source plan, QA admission and the original sealed report, including integrity,
  Task/candidate/implementation, producer agent/run/context and complete criterion coverage.
  Source scope, Task snapshot, original artifacts, dispatch, approved stage chain and parent owner
  must match; only `prior_run_ids` may grow. Current native checkpoint/policy/parent cursor and
  allocation still pass ordinary production freshness checks.
- If source Reviewer was admitted, bind its digest and the exact QA it consumed. Otherwise the
  reference is absent, the source must still have no Reviewer admission, and exactly one sealed
  QA artifact must match the admitted QA run. No orphan or ambiguous artifact is authority.
- If source used controlled execution, require its successful COMPLETED QA receipt with no
  effective failure. Receipt lineage is validated against that plan/authorization/admission.
  Command success alone never creates QA PASS. UI scenario cannot change while reusing QA.
- Successive Reviewer-only plans flatten to the original QA proof, not a chain of synthetic QA
  producers. Latest-attempt validation also checks the immediately preceding Reviewer for a verdict.
- `retained_qa` and native `inputs.accepted_qa` are mutually exclusive. Missing optional fields
  remain excluded from historical wire hashes. No historical event, artifact, approval or completion
  is rewritten. The original terminal Task and its event history stay unchanged.
- Fresh execution identity, current policy, independent Reviewer and a new exact human approval
  remain mandatory. Consumed plans are never replayed. Runner supplies the original plan,
  implementation and QA artifact as required Reviewer context; it never invokes QA for reused QA.
- Reviewer-only completion has no new `qa_invocation_sha256`, embeds the exact original QA and
  binds the new Reviewer admission/report. Review REJECT still routes through normal remediation.
  Only QA PASS + independent Review APPROVE allows normal delivery adoption and parent DONE.
- Controlled Reviewer build/test/UI run independently in its own isolation. Do not replay QA's
  actions or recapture QA images. Preserve approved supplementary UI/Manager advice and any exact
  prior-visual reference; never expand evidence history implicitly.
- Console approval must explicitly say only Reviewer will execute and show retained QA artifact,
  source plan/admission and Reviewer route. It must not label standalone QA as a native Task event.

### 3.1 Current-candidate plan lookup

`CandidateVerificationEntry.latest_project()` may scan an append-only ledger containing plans for
many historical candidate commits. Each `verification-plan-<sha>.json` must first be read through
the scoped `FileRecoveryStore`, which preserves filename, Schema, digest, scope and referenced-record
validation. After that typed read, compare `plan.inputs.candidate_revision` with the candidate SHA
from the freshly inspected terminal source. Plans for another candidate are historical facts and are
not eligible for the current recovery, so they must not invoke `NativeVerificationFacts.validate()`.

Only plans whose candidate SHA matches the current source receive the full current-fact validation
(checkpoint history, artifacts, Git, policy, allocation and retained evidence). This is a per-call
read bound, not a cache: a new snapshot reopens and validates the complete plan ledger so newly
published or corrupted records cannot be hidden. A malformed or tampered historical plan still
fails closed during its typed read; candidate filtering must never turn integrity errors into an
ignored record.

## 4. Validation & Error Matrix

| Facts | Result |
|---|---|
| Same inputs, admitted/sealed QA PASS, Reviewer context/provider interruption | Fresh Reviewer-only plan |
| Same scenario, successive Reviewer interruptions | Same original QA proof, new Reviewer identity |
| No new exact approval | Refuse execution before any agent/actions |
| No QA admission, no unique sealed QA, QA FAIL, any sealed Review, or completion | No retained QA selection |
| Newer failing/completed attempt | Reject an older proposal's reuse; do not search older PASS |
| Missing source record, forged digest, candidate/Task/stage/dispatch/parent mismatch | `RecoveryRecordMissing` / `RecoveryRejected` |
| Sealed report tampered on disk | `ArtifactCorruption`; no model call |
| Controlled QA receipt missing, blocked or uncertain | Refuse retained QA |
| UI scenario differs | Refuse Reviewer-only proposal/plan |
| Old plan lacks both reuse sources | Ordinary QA → Reviewer; old hash unchanged |

## 5. Good / Base / Bad Cases

- Good: QA PASS → Reviewer HTTP failure → restart → new exact approval → only Reviewer → DONE.
- Base: no durable trusted QA checkpoint → new independent QA → Reviewer.
- Bad: scan all artifacts for any PASS, create a fake `qa_passed` event, synthesize partial completion,
  silently replay consumed approval, or use a completed/rejected attempt as an interruption.

## 7. Wrong vs Correct

```python
# Wrong: completion is absent, therefore nothing from the attempt is reusable.
qa = run_qa(candidate)
review = run_reviewer(candidate, qa)

# Correct: typed checkpoint proof is distinct from native Task events and completion.
qa = admission.reusable_qa(inputs)
if qa is None:
    qa = run_qa(candidate)
review = run_independent_reviewer(candidate, qa)  # fresh approval + at-most-once admission
```

The architectural boundary is role progress versus overall completion: durable admitted artifacts
can be recoverable without pretending that the interrupted attempt already completed.
