# 历史任务详情不能冒充当前需求状态

## 问题和目标

需求历史和成员队列已经正确标记历史子任务，但点击“查看当次执行记录”后，任务详情仍显示
“当前进展”“当前执行 · 已阻塞”和旧恢复下一步。同名 K1 当前正在执行时，用户因此可能误认为
需求再次阻塞并按照旧建议操作。历史身份必须在进入详情后保持，用户能直接看见当前需求的位置。

## 范围与验收

- 只以 Project/Requirement 精确父归属及当前 scope source ID 区分历史任务；不能按标题或终态猜测。
- 历史详情首屏、dialog 名称、结果 badge 和第一章节明确为历史/当次，注明不代表当前需求。
- 当次原因、处理方、建议、重试时间、暂停记录都用历史措辞，不承诺旧恢复/审批入口或自动执行。
- 直接显示 exact 父需求的当前阶段和状态，并提供只读“查看当前需求”入口；事实不明时沿现有
  UNKNOWN 展示契约保持等待工程核验，不猜运行、停止或完成。
- 父需求/当前 sibling 单独更新或 scope 身份替换时历史详情随新事实更新；保留 Task 阅读暂停语义。
- 历史首屏不能将遗留 RUNNING queue 描述成当前运行。原队列、旧建议、QA/Review finding、
  全部执行记录、完整报告和源 URI/SHA 仍可查阅；不改变持久化事实或角色权限。
- 当前 Task 的实时状态和现有 stale/审批门禁保持；孤立或外项目父归属不合成历史身份/父入口。
- 页面渲染与返回父需求都是只读，不发送 POST，不批准或继续交付。

## 验证、存量与回滚

先用实际 app.js::buildDetail 和 DOM visibility 回归证明缺陷，再只跑相关 Node 历史/UI/执行状态
测试、JS syntax 和 diffcheck。扩展已有浏览器历史 fixture，但浏览器验收需单独运行；不能用
fake DOM 声称视觉通过。不跑全量测试、不操作 ASE、不重启、不提交。

存量无 SQL/journal/审批迁移。加载兼容前端资产并刷新原需求，即可从原历史记录查看当前需求；
历史 BLOCKED 与旧建议仍保持原值。回滚本 Task 的展示/spec/test 修改并刷新即可，持久事实不变。
