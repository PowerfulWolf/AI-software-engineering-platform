# Completed-output rescue implementation

## Result and scope

Added the distinct `completed_output_rescue` execution-baseline purpose for an
exact native Coder completion whose report was never accepted. The original
FAILED / WORK_INTERRUPTED outcome and unknown report content remain unchanged.
The completion proof establishes only the separately sealed native stop, not a
successful implementation or a Schema rejection.

The public proposal omits `target_base_ref`; the production collector resolves
the trusted current execution base while holding the existing Task lock and
idle SQL fence. The service independently checks the same base. Existing
source-rebind proposals still require a different explicit target, and legacy
unknown-stop rescue remains a separate purpose with its existing containment
authority.

The new plan preserves the same Task, branch, worktree, HEAD and complete legal
draft. It requires exact completed proof, original claim/publication facts,
current full inventory, both legal captures, frozen permissions, no accepted
implementation and ordinary remaining Coder work budget. The exact plan can
only be approved with engineering authority as PAUSE; continuation is a separate
latest-bound RESUME. Consumption revalidates the original proof, captures,
complete inventory and policy immediately before the SQL write. Replay uses the
existing reservation and does not refund or duplicate work budget. Subsequent
execution obtains a new Run/Context/claim and must pass independent QA/Review.

The binding carries `completed_output_sha256` only for the new purpose. Absent
new optional fields remain excluded from old canonical serialized facts. A new
binding inherits the previously accepted native-rule epoch and context lineage;
it does not silently adopt rules merely because source code has changed.

## User interaction

Console operation contract version 5 exposes “准备保留进度的恢复方案” without
asking the user for a Git SHA. Typed timeout/provider failures, alternate known
result routes, foreign facts and exhausted budgets exclude this specialized
entry. Eligibility is established by the backend, so preparation copy says the
platform will check the prerequisites.

An exact prepared plan explains the completed stop, unknown original report,
normal work cost, approval as PAUSE and separate continuation. Copied reports
show the current exact plan and label an older inconclusive investigation as
history. They no longer tell the user to repeat an obsolete investigation or
seek a maintainer when an actionable current plan exists. Exact active RESUME
operations show that the platform is preparing continuation and the next role
execution has not yet started; unrelated operations cannot establish this state.
Task detail links to its owning requirement only for the current same-Project
owner.

Independent review found two initially missed cases. An exactly matching older
unknown-stop investigation could hide the new plan's PAUSE control; the exact
current completed plan now takes precedence, the older investigation is shown
as history, and detached legacy/HANDLE/RESOLVE callbacks cannot replace the new
plan. Proof and action view signatures include the exact plan digest, so the
existing DOM changes correctly during preparation and invalidation without a
reload; read-only investigation remains available. A
standalone queue-release schema regenerated its embedded Binding without the
purpose gate; both standalone writing passes now guard root and embedded
definitions. Published and fresh standalone semantic tests cover the new
proof/PAUSE and retained legacy gates.

## Cross-layer checks

- Public typed command, five published Schemas, regeneration patcher, service
  plan/binding validators and SQL queue consumer agree on purpose and PAUSE.
- New regeneration guards run after the legacy guards, so fresh generation
  retains both contracts; non-new bindings cannot carry the new proof field.
  Every standalone envelope receives the same embedded gates, including the
  final rewriting pass. Generated shape parity is checked separately from the
  authored semantic cross-field guards.
- UI capability checks use contract version 5, typed facts and exact current
  scope, intent, revision, WorkItem, source and binding identities.
- Production baseline recovery never changes the old outcome, a role verdict,
  protected main, permission scope or direct work queue history.

## Deployment and stock-data treatment

This task was developed in the isolated `task/completed-output-rescue` checkout.
No production ASE operation, database mutation, deployment, restart or Coder
worktree mutation was performed by the implementer. Integration and production
maintenance remain with Root after independent review.

There is no database migration or direct repair of old records. For a qualifying
existing requirement, load the compatible service at an idle boundary, refresh
that requirement, prepare/check the target-free recovery plan, inspect the exact
plan, approve PAUSE, and explicitly RESUME the existing requirement. Keep its
Task, old failure, full draft and audit history. Do not recreate the requirement
or reopen old queue rows. A timeout, unknown stop, known provider error, missing
proof or incompatible draft is outside this purpose and still requires its
corresponding truthful recovery route; this patch does not convert such facts
into completion.

## Rollback

Before new-purpose facts are created, revert this change at a verified idle
boundary. Once such facts exist, retain readers compatible with the new purpose
and proof field, preserve immutable history, and prevent new proposals if the
capability is withdrawn. Restoring earlier queue rows or discarding the draft is
not a rollback procedure.
