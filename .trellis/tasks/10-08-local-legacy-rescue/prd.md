# 无需整机重启的旧执行恢复

## 目标

修复原 K1 旧 Coder 执行结果/停止记录缺失时，只能通过整机重启准备恢复方案的问题。平台负责实际核验、完整保存进度和说明前提；用户只批准明确的恢复决定，不能依赖手工改库、清空现场或重复失败点击。

## 已知事实

- 原执行有精确 invocation-start 和历史 claim，但无结果、原停止和现场 receipt。普通服务升级不补造这些历史事实。
- 当前旧恢复分支强制 `booted_at > started_at`，在准备计划前拒绝；新版服务成功启动不改变此约束。
- 用户已完成旧服务维护停止并启动新版；当前无活动 Console Operation。此事实单独不足以证明任意旧子进程停止。
- 用户授权修复平台；当前不委托恢复审批或启动 K1 Coder。

## 范围与验收

- 增加有真实本机核验及明确工程授权的非重启恢复路径；证据不充分时保留等待并说明下一步。
- 保留同一 Requirement、Task、原分支、完整合法草稿和历史 UNKNOWN，仍经独立 QA/Review 验收。
- 准备、审批、SQL 消费及重放均重新校验精确工作现场和当前执行隔离，不把空队列/租约过期/服务 PID 退出当旧停止事实。
- 用户不能通过请求体注入进程、日期或隔离事实；没有秘密和任意 shell/path 权限扩张。
- 前端明确区分平台检查、用户授权、已安排新执行，中文错误不泄露 Pydantic payload。
- 真实公共 Console fixture 覆盖无整机重启成功、活动执行/未知观察拒绝、现场漂移、授权绑定与重复消费。
- 只运行增量测试、相关 Ruff/mypy 和 Schema 合同检查。

## 存量与回滚

无需修改旧 Task/Run/审批或 SQL 表。新代码以追加精确计划/授权/新执行事实恢复原需求；生产需求暂不审批/执行。回滚前受控停止服务，回退本次提交，保留所有新旧 immutable facts。

## 设计问题

正在研究现有原调用的执行锁/本机执行边界以及可达的停止证明。不能因用户体验要求删除停止校验；可信新工程处置与旧历史结果严格分开。
