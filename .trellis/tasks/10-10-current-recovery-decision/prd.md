# 当前精确恢复决定的展示

公开 GET 原 K1 在恢复准备成功后已有当前 checkpoint 的精确审批，但需求标题仍显示旧执行
阻塞，建议仍说“当前无需产品操作”，下方却要求工程授权者“批准并继续”。这使使用者不知道
该等待平台还是批准方案。

## 目标与验收

- 当前 Project/checkpoint 的可信、未消费 exact approval 可用且没有新活动操作时，需求显示
  “待工程确认”，清楚说明尚未继续执行、批准者及批准后的行为。
- 原失败与终态 Task 保持不可变，以“原执行历史”保存；不作为当前建议操作。
- current source 不可读、跨 Project、旧 checkpoint、已消费审批、能力缺失或新操作出现时，
  不使用旧审批作为当前决定。既有提交、角色执行、精确身份门禁不减。
- 当前 queue 的真实执行/调度事实仍优先，不能用准备过的审批宣称已经开始执行或完成。
- 只读 presentation 改动，不操作生产 ASE，不改数据库或历史 Operation，不审批、不提交。

## 验证与回滚

使用真实 app.js 的 Node VM，以公开 GET 中 STOPPED + terminal BLOCKED + exact approval
缩成最小 fixture，先 RED 后 GREEN。运行新用例与受影响状态/审批用例；不跑全量测试。
回滚仅撤销当前展示逻辑、增量测试与知识，所有历史事实与审批摘要保持原样。

## 存量数据处置

无需数据库迁移。加载新前端并刷新原需求；仅重新计算当前决定和历史展示。平台/工程输入
变化仍需要重新准备精确方案，前端不会自动批准或继续已有需求。
