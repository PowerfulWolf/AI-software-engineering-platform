# 交付主链路稳定性审查

## 目标

先停止以真实需求作为逐个补丁的试验场，审查并稳定 ASE 从需求到交付的完整主链路，再由 ASE
继续原业务需求。目标是可恢复、可解释、权限明确、知识可积累的团队工作流，而非承诺发现所有 bug。

## 背景与已确认事实

- 用户于 2026-09-27 批准创建和规划，随后明确授权全阶段审查、发现即修复及不合理架构调整。
- 当前没有 RUNNING/QUEUED Console Operation；原需求 BLOCKED，原候选
  `9ac7c9ee830df548571db55ec5cf809e613467ba` 与所有审计事实保留。停止派发是操作约束，不伪造平台暂停状态。
- 最新真实阻塞为 `LEGACY_KNOWLEDGE_SCOPE_CHANGED`：原 QA 检索快照没有文档，恢复时带入三份
  父需求封存的项目原生文档。此前测试没有覆盖这一真实上下文组合；本轮已修复并完成隔离回归，
  尚未加载到真实业务交付。最终结果见 verification.md。
- 之前已修正审批循环、知识等待交接、旧上下文说明摘要兼容、非终态 QA 的平台异常恢复与固定诊断；
  新生成数据的测试通过，不代表存量多次恢复链已经满足端到端契约。
- 工作区存在大量前期未提交改动，不能重置、覆盖或批量归为本任务成果。
- 相关任务：`09-25-joint-approval-delivery` 保留真实交付过程；`09-25-team-evolution-audit`
  保留组织职责和知识演进能力建设。本任务只承接影响交付可靠性的审查与修正。

## 需求

- R1：画清需求准备、Product 审批、Design、Plan、派发、Coder、QA、Reviewer、验收和交付的事实链，
  区分模型决策、确定性服务、人工权限和 Console 展示。
- R2：审查正常执行、重启、知识等待、环境阻塞、角色失败、终态恢复、源码前提修复、多目录回接的
  Context/Task/候选/审批/租约绑定，消除已证实的路径差异；未知项必须有调查或明确覆盖结论。
- R3：Manager 拥有环境/数据/权限协调；平台缺陷、业务缺陷、知识缺口和外部环境不得混为一类。
  无进展的重试不得重复消费审批或无意义重跑 Coder/QA。
- R4：知识检索快照、角色可见的批准上下文、规范、能力授权分别建模；历史快照不能静默扩展，
  已批准的解答必须跨正常恢复可用。知识发布/前端可见/后续需求使用的既有闭环纳入回归。
- R5：每项确认缺陷先做可失败的测试，再修复最小共同根因；增加真实 Git/隔离 MySQL、历史契约
  fixture、中断恢复和拒绝测试，不能只靠 mock happy path 或测试数量判断可交付。
- R6：形成明确的恢复交付门槛与交接清单，通过后提出恢复原需求；仍由 ASE 生成独立业务验收结论。
- R7：覆盖知识导入、显式选择、冻结、检索、缺口解答、发现收集、独立发布、页面展示和后续需求复用；
  覆盖所有 Agent 的职责、上下文相关性/预算/身份隔离及队列领取/续租/释放/幂等；架构问题允许局部重构，
  但不能删除审批、完整性或独立验收门禁来消除报错。

## 验收标准

- AC1：审查矩阵每个主阶段都有入口、权威事实、权限、失败分类、恢复点和测试证据；未覆盖项明确列出。
- AC2：已确认的阻断交付/破坏授权或事实完整性问题全部关闭；其余风险逐项说明影响和处置，不笼统称零 bug。
- AC3：隔离完整流程到 DONE；同候选独立 QA PASS 与 Reviewer APPROVE 不可跳过，不自动 merge。
- AC4：关键中断点在新进程恢复，审批按精确计划消费，保留候选和原角色进度，无重复 Coder或既完成副作用。
- AC5：历史上下文/计划/快照按原摘要读取，真实存量组合有脱敏可复现 fixture；新增知识不改写当前冻结事实。
- AC6：错误能够定位到安全的固定分类与下一步责任；前端状态不把模型调用成功或环境修复误报为验收成功。
- AC7：相关 lint、严格类型、Schema parity、单元/契约/前后端集成测试通过，MySQL 测试串行且只使用隔离库。
- AC8：规范与审查结果落盘；最终清单明确哪些已证明、哪些仍需真实验证，用户确认恢复后才继续原需求。

## 不在范围内

全平台重写、新产品功能、分布式基础设施、单 Task 并行 DAG、角色自行扩权、安装/升级环境、
业务代码代写、真实用户数据迁移、历史事实覆写、自动部署或合并。Swift/UI 作为一个能力适配案例，
不能变成所有项目的默认前提。必要的局部重构须服务于已证明的契约缺陷，并按小切片验证。
