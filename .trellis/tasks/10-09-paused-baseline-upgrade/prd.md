# 保留进度后暂停，再更新基线并明确继续

## 目标

修复原需求旧执行恢复与新源码/工程规范更新无法衔接的问题。用户可以先保存合法开发进度并
保持暂停，在同 Requirement/Task/原分支/工作区检查并批准精确版本及规范差异，再明确继续。
此能力适用于任意目标仓库；ASE 自身作为目标项目只是更频繁地触发，不新增自举特例。

## 已知事实

- 原 K1 完整 READY 救援方案绑定旧代码 `0a562f4`，现批准即调用 resume_delivery。
- SQL 基线消费一律设置 READY，单纯取消 Host 的 resume 无法防止 dispatcher 自动领取。
- 主分支更新包含 AGENTS/README/CI/Trellis 等 native rules 时，源码方案在生成前拒绝，
  所谓“另行确认规范或范围”没有公共可操作路径。
- 同 Task 更新不替换 native rules 的 prompt/knowledge 输入；取消拒绝会产生新代码配旧规范。
- K1 有完整 9 个修改文件和 15 个新增文件；不能清空、手工改审批事实或退款。

## 范围与验收

- [x] 新保留/源码更新操作以持久工程暂停阻止同步/独立 dispatcher 或普通继续自动启动。
- [x] 暂停后源码更新入口仍可用，显式继续绑定最新 Task/工作项/源码/规范/方案，旧决定拒绝。
- [x] 更新代码允许提出精确完整 native rules 增改删差异，需独立明确确认对应 digest。
- [x] 当前规则读取来自获批的不可变 Git 版本，正文脱敏且有原始/渲染摘要，不受 checkout 漂移影响。
- [x] 同一有效规则版本同时进入 Coder/QA/Reviewer prompt 与知识查询 Context。
- [x] 原 preparation、Product/Design/Plan、Task.base_ref、hard policy、权限与历史保持。
- [x] 救援仅消耗原应有下一轮额度；后续暂停更新与继续不重复扣费，重启重放幂等。
- [x] 旧 Operation/READY 方案/绑定缺省字段的 bytes 与 digest 兼容；普通继续无法绕过暂停。
- [x] UI 明确展示“进度已保留，交付暂停”，代码更新与真正开始执行是分别可辨的操作。
- [x] 隔离公共 Host/Console 测试完成：暂停零模型调用→新代码/规范更新零调用→明确继续→独立 QA/Review。
- [x] 仅增量 tests、格式/类型检查与独立审查，完成存量数据处置和回滚说明。

## 方案取舍

采用同需求追加工程输入版本和独立继续授权。手工 rebase 会使方案/现场/权限的摘要失配，
新建同名需求会丢失当前连续性，均不作为解决办法。不引入新 Task 阶段、并行角色、自动 merge、
权限扩张或预算重置；不替用户审批/继续生产 K1。

## 存量与回滚

原 READY 方案须能在新版本使用“保留进度并暂停”入口；无需改库绕过批准。新增暂停/规则版本
一旦写入，应保持兼容读并向前修复，不把新事实交给不认识它们的旧版本。生产加载仍使用
受控服务维护流程，与 K1 源码更新及执行批准分开。
