# 平台设置统一排版方案

## 目标

重排“平台设置”的基础配置、MySQL、模型路由三个页面，使它们共享同一套信息架构、视觉层级和间距规则。目标是简洁、清晰、紧凑但不拥挤；本任务不改变字段、保存协议、权限、密钥或运行时生效语义。

## 必须保留的契约

- 左侧局部导航仍包含基础配置、MySQL、模型路由。
- 三个页面共用一个草稿，一次原子保存；切换子页不丢失未保存内容。
- 配置状态、配置文件路径、保存反馈和需要重启提示必须保留。
- MySQL DSN 与 API Key 仍是 write-only，页面不回显已保存的 secret。
- `live_model_execution` 保留为真实的运行时安全闸门；UI 必须明确说明关闭会拒绝模型执行，而不是切换到 fake Agent。
- 启用模型目录项不等于把它加入 Agent fallback；Agent 主模型与备用顺序语义不变。
- 只调整浏览器信息架构和样式，不改 Settings API、配置 Schema 或持久化格式。

## 现状问题

1. 三个页面采用不同的内容结构：基础配置是 section + grid，MySQL 是散列字段，模型路由是说明、卡片和 Agent 分配混合。
2. 页面标题、状态、配置路径、区块说明和字段帮助文字没有稳定的视觉层级。
3. 双列字段卡在长文本和不同高度帮助文案下容易产生大块空隙。
4. 模型路由永久展开全部 Provider 字段，页面过长，目录管理和 Agent 分配主次不清。
5. 保存区虽然共享，但与页面内容的状态反馈关系不够明确。

## 三种结构方案

### A. 分组表单行（推荐）

保留左侧导航；右侧使用固定宽度内容区。每个页面由相同的页面头、section header、字段行和 sticky 保存栏组成。桌面字段行采用 `200px label + flexible control`，帮助文字跟随 label；section 之间用细分割线区分。

优点：信息位置稳定、扫描快、适合频繁修改，能直接适配当前共享草稿和原子保存结构。缺点：首次配置时没有步骤引导感。

### B. 摘要卡片 + 抽屉编辑

右侧默认只展示每个模块的当前摘要和状态，点击“编辑”后在抽屉内修改该模块。

优点：默认页面最简洁，复杂 Provider 字段不会撑长页面。缺点：操作路径更深；跨模块检查和一次原子保存的关系不直观，键盘与小屏抽屉状态更复杂。

### C. 单页步骤式配置

把基础配置、MySQL、模型路由改为一个从上到下的三步流程，每步完成后进入下一步。

优点：适合首次安装。缺点：日常只改一个配置时效率低；长页面和验证定位更复杂，也弱化了现有局部导航。

## 推荐决策

采用 A。它不引入新的交互状态，能用最小改动统一三个页面，并与现有“共享草稿 + 一次保存”契约自然匹配。模型路由只在 section 内使用渐进展开，避免退化成卡片套卡片。

## 统一页面骨架

```text
┌──────────────┬─────────────────────────────────────────────────┐
│ 平台设置     │ 页面标题                         [当前已生效]   │
│              │ 一句话说明                                      │
│ 基础配置     │ 配置文件  /path/to/config.json                  │
│ MySQL        ├─────────────────────────────────────────────────┤
│ 模型路由     │ Section 标题                                    │
│              │ Section 说明                                    │
│              │                                                 │
│              │ 字段标签/帮助     [控件                         ]│
│              │ 字段标签/帮助     [控件                         ]│
│              ├─────────────────────────────────────────────────┤
│              │ Section 标题                                    │
│              │ ...                                             │
│              ├─────────────────────────────────────────────────┤
│              │ 未保存/重启提示                  [保存设置]     │
└──────────────┴─────────────────────────────────────────────────┘
```

## 三个页面的信息架构

### 基础配置

1. 平台身份
   - 平台数据目录
   - 唯一 Team（只读）
2. 运行环境
   - Codex 可执行文件
   - Web Console 端口
   - 允许调用真实模型：全局安全闸门；关闭后拒绝模型任务，不切换到模拟执行
3. 执行与重试策略
   - 使用紧凑表格：角色 / 工作次数 / 临时故障 / 说明
   - QA、Reviewer 的工作次数显示 `—`，说明有效否定结论回到 Coder，不伪装成重试
   - Manager 作为 section footer 说明，不占一行伪配置

### MySQL

1. 连接配置
   - 启动变量名作为只读 metadata
   - MySQL DSN 作为唯一主要输入
   - write-only 规则显示在输入附近，不放在页面顶部形成悬空说明
2. 连接验证
   - “测试连接”和结果位于同一 action row
   - 结果使用行内成功/失败状态，不改变页面布局
   - 安全和重启说明作为 section footer

### 模型路由

1. 可用模型目录
   - section header 右侧放“添加路由”次按钮
   - 每条路由默认显示 Provider、Model、Reasoning、类型、启用状态的单行摘要
   - 点击一条路由后在本行下方展开 Endpoint、API Key 环境变量、API Key、图像输入和删除动作
   - 同一时刻只建议展开一条，减少纵向噪声；不改变实际 draft 内容
2. Agent 路由分配
   - 每个 Agent 一行：角色说明 / 主模型 / fallback 数量与“管理”动作
   - fallback 编辑在该行内展开，并保留添加、移除、上移、下移语义
   - 禁止 Provider 卡片再嵌套 Agent 卡片

## 视觉与间距规则

| 项目 | 规则 |
|---|---|
| 右侧内容宽度 | `max-width: 960px`，避免超宽屏拉散字段 |
| 页面头到首个 section | 24px |
| section 上下间距 | 28px；由分割线统一承担，不叠加子元素 margin |
| section 标题与说明 | 6px |
| section 说明到内容 | 18px |
| 字段行 | 桌面最小 68px；相邻字段 16px |
| label 列 | 200px，标题 14px/600，帮助 12px/1.5 |
| 控件高度 | 40px；文本区域按内容增长 |
| 列表行 | 52–60px；展开区额外 16px 内边距 |
| 保存栏 | 上边框 + 14px/20px 内边距，sticky bottom |

Section header 和字段行复用同一条 `200px + 24px + flexible` 网格基线：Section 标题与字段标签左对齐，Section 说明、输入控件、行内动作和 footer 与右侧控件列左对齐。备用模型等可排序列表使用固定的“序号 / 内容 / 操作”列，不能由模型名称长度决定按钮位置。

避免用大量阴影和独立卡片制造层级；页面面板保留一个容器，内部主要依赖排版、留白和细分割线。

## 响应式

- `>= 900px`：左侧 224px 局部导航；字段使用 label/control 两列。
- `600–899px`：局部导航变为顶部横向 tabs；字段仍优先两列，空间不足时堆叠。
- `< 600px`：字段上下堆叠；表格转为按角色分组的行；保存按钮占满一行。
- 小屏不改变信息顺序、字段名称、保存范围或 secret 规则。

## 验收标准

- 三个子页使用同一页面头、section、字段行、说明、反馈和保存栏组件/类名。
- 任意子页首个 section 起始位置一致；相邻 section 的分割线与上下间距一致。
- Section 标题与所有字段标签共享左侧基线；Section 说明、控件、验证动作和 footer 共享右侧基线。
- 同一排序列表内的序号、模型名称和操作按钮逐列对齐，长短名称不能推动按钮横向漂移。
- 基础配置模块边界明显，执行与重试策略不再出现过大的标题/说明空隙。
- MySQL 测试动作与反馈形成一个明确模块。
- 模型目录与 Agent 分配是两个同级模块；默认只展示紧凑摘要，展开编辑不产生卡片嵌套。
- 900px 与 600px 两个断点下无横向溢出、遮挡或 sticky 保存栏覆盖最后一行。
- 增量验证只运行设置页相关 DOM/浏览器测试；不得执行全量测试。

## 实现边界与回滚

预期只修改 `team_view/app.js`、`team_view/style.css`、设置页相关浏览器测试和本任务文档；如无需改变契约，不修改 API、Schema、Python 后端或存量配置。回滚时恢复前端渲染与样式即可，存量数据无需迁移。
